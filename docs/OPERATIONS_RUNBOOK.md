# Operations and Recovery Runbook

## Production configuration

Set these environment variables before deploying the API:

- `APP_ENV=production`
- `AUTH_SECRET`: a long random secret managed by the deployment secret store. The API refuses production startup with the development default.
- `CORS_ORIGINS`: the exact trusted storefront origins, comma-separated.
- `SMTP_HOST`, `SMTP_FROM`, and the appropriate `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, and `SMTP_STARTTLS` values. Production startup fails without the SMTP host and sender because password recovery and order notices require email delivery.
- `FRONTEND_BASE_URL`: the canonical HTTPS storefront URL.
- `DATABASE_URL`: the production database URL.
- `NEXT_PUBLIC_STORE_ID`: the approved tenant ID served by this storefront deployment.
- `DELIVERY_FEE_RWF` and `MIN_ORDER_RWF`: server-side checkout rules.

Never expose `AUTH_SECRET`, SMTP credentials, or database credentials to the frontend.

## Health checks

- `GET /health` is a lightweight liveness check.
- `GET /health/ready` performs a database connectivity check and returns HTTP 503 when the database is unavailable.
- Platform administrators can inspect `GET /api/v1/platform/system-health` for database status, production configuration flags, pending store approvals, and authentication throttling activity.

Alert on readiness failures, sustained checkout errors, growing 5xx rates, repeated authentication throttling, failed SMTP delivery logs, and unexpected inventory conflicts. Configure external log aggregation and alert delivery in the deployment environment.

## Backups

Run from `apps/api` with the production database credentials loaded into the environment:

```powershell
python scripts/backup_database.py --output-dir ./backups
```

The utility supports file-backed SQLite and PostgreSQL (requires `pg_dump`). It writes a backup and a JSON manifest containing the SHA-256 checksum. Store backups outside the application host, encrypt them at rest, restrict access, and apply a retention policy. Schedule backups through your infrastructure scheduler rather than relying on a developer workstation.

## Restore procedure

1. Put the application into maintenance mode and stop writes.
2. Retrieve the backup and its matching manifest from protected storage.
3. Verify the backup checksum and confirm the target database carefully.
4. Create a safety backup of the current SQLite database if applicable.
5. Run the restore command with explicit confirmation:

```powershell
python scripts/restore_database.py ./backups/virtual-store-YYYYMMDDTHHMMSSZ.sqlite3 --confirm
```

For PostgreSQL, the backup must be a custom-format `.dump` generated by `pg_dump`; restore uses `pg_restore`. The restore utility refuses to run without a manifest, a matching checksum, and `--confirm`.

6. Run migrations and smoke tests, including tenant isolation, login/MFA, catalogue reads, basket checkout, order history, receipt generation, and inventory reconciliation.
7. Reopen traffic only after readiness checks and business-critical smoke tests pass.

## Release and rollback

Deploy migrations before routing traffic to code that requires the new schema. Keep the previous application image available for rollback, but do not roll application code back across incompatible schema changes without a tested database migration plan. Perform a restore drill in a non-production environment on a regular schedule and record its duration and outcome.

## Security notes

- Store sessions use HttpOnly cookies; unsafe cookie-authenticated requests require a CSRF token.
- The development admin-key bypass is disabled when `APP_ENV=production`.
- TOTP MFA is optional. Recovery codes are not currently implemented, so users should not enable MFA unless they can reliably access their authenticator.
- The in-process authentication throttle is a single-process baseline, not a distributed rate limiter. Multi-replica production deployments should move throttling to a shared Redis or gateway service.
- Sandbox payment simulation is not a real payment-provider integration. Production payment processing requires signed webhooks, idempotent provider event handling, and reconciliation.
